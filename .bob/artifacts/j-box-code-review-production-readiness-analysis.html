🔴 Production Blockers

These will prevent the system from working correctly under real load or will expose user data / money integrity errors.

BLOCKER
Shared singleton ScopedSql clients are not request-safe
apps/product/src/lib/db.ts · lines 10–11, 129–141, 163–176

tenantClient and platformClient are module-level singletons. executeTenantQueries calls requireOrganizationContext() at execution time (correct), so the RLS context is per-call. However createScopedClient captures the execute closure at construction time and returns a shared object. Two concurrent requests therefore share one ScopedSql instance. The instance itself is stateless, so in practice this is safe — but only because today's transaction() implementation just collects statements and passes them to the executor. If transaction() is ever extended to accumulate pending state (e.g. a statement buffer), concurrent requests will corrupt each other's state without any obvious failure signal.

The deeper issue: tenantClient is recreated only once per process. This is fine for the executor, but if anyone stores in-progress state on the client object the design breaks. Recreating the client per-request (cheap; it's a thin wrapper) would make the safety invariant structural rather than a comment. Alternatively, add a clear note that ScopedSql must remain stateless.

BLOCKER
Storage is local-disk only — not survivable on Vercel, breaks multi-machine Fly deployments
apps/product/src/lib/storage.ts · apps/product/src/app/api/requests/route.ts

Service-request photos are written to the local filesystem (STORAGE_DIR). This works on a single Fly machine with a persistent volume, but:

  • Vercel deployments (the current CI target) have no persistent filesystem. The product app also has a vercel.json and a .vercel/ output — photos uploaded to a serverless function will be silently lost on the next invocation.
  • Any Fly deployment with multiple machines (scaling to 2+) means uploads on machine A are invisible on machine B.
  • The health check (migration 004) does not verify storage availability.

The code acknowledges this with "Local object storage for the MVP," but it is a hard blocker before opening to a second user. Replace with an object-storage provider (R2, S3, Vercel Blob) keyed off STORAGE_BACKEND.

BLOCKER
MFA disable endpoint stub — directory exists but route file is absent
apps/product/src/app/api/auth/mfa/disable/ (empty directory)

The MFA enrollment flow (/api/auth/mfa/enroll, /api/auth/mfa/setup) is implemented. The disable endpoint directory exists but contains no route.ts. Any UI that links to POST /api/auth/mfa/disable will get a 404. A user who loses their authenticator device has no server-side recovery path — they cannot regain access without a direct database intervention. This is a support and compliance blocker for any tenant that has MFA enabled.

The missing path should perform: verify password (re-auth), verify current TOTP token, clear platform_users.totp_secret, set organization_memberships.mfa_required = false, and revoke all active sessions (force re-login).

BLOCKER
Onboarding rate-limiter uses in-process memory — honeypot check runs after JSON parse
apps/product/src/app/api/platform/onboarding/route.ts · lines 25–39

Two problems in the signup route:

  • Rate limit is in-process memory only. The route uses rateLimit() (not rateLimitWithFallback()). On Vercel each invocation is a cold function — the bucket is empty on every request. With capacity 5 and no shared state, a single IP can sign up five times per cold start. The login route correctly uses rateLimitWithFallback(); onboarding does not. This is the highest-value abuse surface on the platform (provision cost, NVIDIA API cost).
  • Honeypot check is post-parse. The honeypot fires after request.json(), which means any parse error (non-JSON body) returns 400 before the honeypot. Bots sending JSON with the field filled will not trigger it. Minor, but if the bot form-submits, the parse still succeeds because fetch(..., body: formData) will fail — harmless in this respect. Still, rate limiting must be fixed first.

🟠 High Severity

HIGH
control-db.ts pool has no SSL for production — DATABASE_URL only
apps/control/src/lib/control-db.ts · lines 26–32

The product app's db.ts correctly applies ssl: { rejectUnauthorized: true } for non-localhost connections, falling back gracefully for local dev. The control app's control-db.ts creates its pool with no SSL config at all. On Neon (which requires SSL by default in the connection string), this works because pg can negotiate SSL from the URL — but a misconfigured URL or a future database move may silently use plaintext. Align with the product app's pattern.

HIGH
verifyCustomerAccessGrant fetches organization_id from a separate query — TOCTOU gap
apps/product/src/lib/customer-access-grants.ts · lines 181–184

After validating the token, the function issues a second SELECT app_current_organization_id() to populate scope.organizationId. The token was already validated against the grant row in the same DB session, so in practice this is the same value. However, the grant row already carries organization_id — it is read from the database in the first query. The code should use grant.organization_id directly. The extra round-trip is a latency cost and introduces an unnecessary query. It is also confusing: a reader sees an empty organizationId: '' in the scope literal and has to trace two steps to understand why it's safe.

HIGH
service-request body read entirely into memory before tenant resolution
apps/product/src/app/api/requests/route.ts · line 43

The storefront's POST /api/requests calls request.formData() — which buffers the entire multipart body including up to 5×8 MB photos (40 MB max) — before verifying that the hostname resolves to an active tenant. An attacker can exhaust server memory by posting large bodies to invalid hostnames. Tenant resolution should happen first (a lightweight hostname lookup), and the body should be read only once the tenant is confirmed. Alternatively, set bodyParser.sizeLimit at the Next.js config level and stream, rather than buffer.

HIGH
Health check is hardcoded to migration 004 — will silently pass on a stale schema
apps/product/src/app/api/health/route.ts · line 18

The health probe checks WHERE name = '004_service_requests_...'. There are now 12 migrations (001–012). A database at 004 will return schema_ready: true even though migrations 005–012 (MFA, outbox, TOTP, invoice creation, etc.) are missing. Load-balancers will route traffic to an instance that will then fail at runtime on missing columns or functions. The check should verify the latest migration by name, or check COUNT(*) = expected, or use the max recorded migration name against the known set.

HIGH
Outbox retry back-off is linear, not exponential; 'dead' message visibility is silent
packages/database/migrations/005_field_identity_and_customer_access.sql · finish_outbox_message · line 508

The retry formula is least(attempts, 10) * 60 seconds. After attempt 10, every subsequent retry is scheduled 10 minutes out, which means 12 total attempts span roughly 55 minutes. The 12-attempt ceiling and dead-letter state exist, but there is no alerting, monitoring hook, or admin surface for dead messages. Once an email hits 12 failures it silently disappears. The platform has no way to know (short of a raw DB query) that a customer never received their estimate link. At minimum, a dead-message count should surface in the health endpoint or a control-plane admin route.

HIGH
provisionTenant: results indexing is fragile and breaks with optional Clerk block
apps/control/src/lib/control-plane.ts · lines 173–179

results[0] and results[1] are assumed to be the organization and domain INSERT rows. But when input.clerkOrganizationId is present, a third statement is inserted at index 2 — shifting nothing (the org/domain are still 0 and 1). However the configRow search (line 179) uses Array.find() looking for a row with row.version !== undefined, which is safe. The concern is that if the provisioning statement order changes, the index 0/1 check on lines 176–177 will silently pass on the wrong result set. Destructuring by a named result or using RETURNING markers would be safer.

HIGH
Estimate update: line pruning operates WITHOUT deleted-line guard for old positions
apps/product/src/lib/estimates.ts · lines 377–384 (pruned CTE)

The pruned CTE deletes line items whose position is not in the new payload. The guard AND EXISTS (SELECT 1 FROM updated) prevents it from running if the header UPDATE matched zero rows (conflict). However, if a technician with estimates.prepare has the estimate open in two browser tabs and saves from both simultaneously, one save will match the header (correct), and the other will be a conflict (correct). The issue is that pruned operates directly on estimate_id = $1, not on the estimate's organization_id. The RLS policy ensures only the right tenant's rows are visible, so this is safe from cross-tenant leakage. But the CTE only guards on EXISTS (SELECT 1 FROM updated) — the DELETE for "orphaned" positions will match rows with estimate_id = $1 without an additional organization_id filter. Under RLS (contractor_app) this is correct because the session is already scoped. The current design is safe but relies entirely on RLS rather than being self-evidently correct from the query alone.

🟡 Medium Severity

MEDIUM
packages/database/src/index.ts and packages/testing/src/index.ts are empty stubs
packages/database/src/index.ts · packages/testing/src/index.ts

Both packages export only export {};. @contractor-platform/database has a rich set of migrations and helper scripts, but no TypeScript API surface — there is nothing to import when applications need to reference migration state or schema types. The @contractor-platform/testing package comment says "Shared fixtures and test helpers" but provides none. Any test that needs shared DB fixtures must either duplicate logic or use untyped scripts. These should either be filled or removed from the workspace to avoid misleading imports.

MEDIUM
Redis rate-limit window key arithmetic drops sub-second precision, causing thundering-herd at minute boundaries
apps/product/src/lib/redis-rate-limit.ts · lines 36–37

The fixed-window key is ratelimit:${key}:${Math.floor(nowSec / 60)}. At the exact turn of every minute, all buckets simultaneously reset — a burst of 60 × capacity requests is possible in any 60-second span that spans a minute boundary (send <capacity> at 00:59, send capacity again at 01:00). The local fallback (rate-limit.ts) uses a token-bucket which avoids this. A sliding-window or token-bucket approach in Redis would be more robust for a login endpoint.

Also: rateLimitWithFallback() short-circuits on the Redis result — if Redis allows, local is never consulted. This means if Redis is configured but the TTL expires (e.g. Redis flushes), all limits reset globally. The fallback only applies when Redis is unconfigured, not when Redis grants access after a reset.

MEDIUM
signEstimate does not capture a snapshot hash until after a second getEstimate read
apps/product/src/lib/estimates.ts · signEstimate function

The sign flow updates estimates.status = 'signed' with a content_hash in a single CTE. However the hash (sha256 over "the rendered document") is computed in the application layer. The "rendered document" used for hashing should be the same content displayed to the customer — but the customer sees the estimate data at the time the sign link was clicked. If the estimate was updated between link issuance and signing (edge case, but allowed in draft state), the hash covers the new content, not what the customer reviewed. The sign endpoint should either (a) lock the estimate row for the duration of the sign attempt or (b) include the estimate's updated_at in the content hash and validate it matches the grant's issuance time. Currently the sign invariant is enforced by the grant's single-use consumption, which is solid, but the content_hash's meaning is weaker than it appears.

MEDIUM
Control plane: no rate-limiting or authentication audit on /api/organizations GET
apps/control/src/app/api/organizations/route.ts · line 44

GET returns all organizations (newest first, no pagination) for any bearer token. With a valid CONTROL_API_TOKEN this is intentional — but there is no rate-limiting, no pagination, and no access log. As tenant count grows this returns an unbounded result set in a single response. A LIMIT + cursor or page parameter is needed before the tenant list grows beyond a handful.

MEDIUM
secret-rotation.ts is unused infrastructure without a call site
apps/product/src/lib/secret-rotation.ts

getRotatingSecretConfig, rotateSecret, buildPreviousKeysJson, etc. are fully implemented but no production code imports them. The actual CUSTOMER_LINK_SECRET rotation is handled inline in customer-access-tokens.ts, which has its own (different) previous-keys JSON parsing. Having two parallel rotation systems — one used, one not — is a maintenance hazard. Either connect secret-rotation.ts to customer-access-tokens.ts and auth, or delete it to prevent confusion.

MEDIUM
createEstimate: customer creation is not rolled back if estimate INSERT fails
apps/product/src/app/api/field/estimates/route.ts · lines 150–154

The comment "Deliberately not rolled back" is present and the reasoning (an orphaned directory entry is harmless) is sound. However, the customer INSERT and the estimate INSERT run in separate db() calls inside withFieldContext(). Each db() call is its own transaction. This is a conscious design choice but it means a failed estimate create leaves an orphaned customer with no estimate, which shows up in the customer list. This can confuse a technician who sees a customer they just created but no associated estimate. At minimum, create the customer only after the estimate validation passes (it currently does — validation happens before the DB calls), but the customer create should be in the same transaction as the estimate create using sql.transaction().

apps/product/src/proxy.ts · line 8 comment

The comment says "Next 16 calls this file proxy.ts; middleware is deprecated." No current public release of Next.js (14 or 15) uses proxy.ts. Middleware is middleware.ts in Next.js 14/15. MEDIUM
allocate_document_number uses INSERT ON CONFLICT DO NOTHING followed by UPDATE — phantom row risk
packages/database/migrations/001_foundation.sql · lines 251–261

The function does an INSERT (which may silently do nothing on conflict) and then an UPDATE with RETURNING next_value - 1. If two concurrent calls for the same (org, kind) pair race on the INSERT, both proceed to the UPDATE. The UPDATE takes a row lock so they serialize correctly. However, the initial INSERT ON CONFLICT DO NOTHING means a missed initial insert is silently swallowed, relying on the UPDATE to find the existing row. This is safe because the UPDATE will always find a row (either the one just inserted or a pre-existing one). However, the NULL check on allocated (line 262) can never actually fire — if the INSERT produced nothing and no row existed, the subsequent UPDATE returns nothing, and allocated stays NULL. The NULL RAISE is reachable only if the row disappeared between INSERT and UPDATE (extremely unlikely, but worth a comment). The UPSERT pattern (INSERT ... ON CONFLICT DO UPDATE SET next_value = next_value + 1 RETURNING next_value - 1) would be cleaner and atomic.

🟢 Low Severity

LOW
content-length bypass: multipart requests without Content-Length header skip size check
apps/product/src/app/api/field/estimates/route.ts · lines 91–94

The body-size check in the POST estimate route only fires when content-length is present (if (contentLength && ...)). Chunked transfer-encoded requests carry no Content-Length header and skip the check entirely. An attacker can send an arbitrarily large body using chunked encoding. Next.js has a built-in 4 MB body size limit for JSON routes but that may not apply to all edge cases. The check should either parse and cap the stream, or rely on a platform-level limit declared in next.config.

LOW
CSP: 'unsafe-inline' in script-src without nonces — reduces XSS protection
apps/product/next.config.ts · line 15 · apps/control/next.config.ts · line 15

Both apps ship script-src 'self' 'unsafe-inline'. 'unsafe-inline' allows any inline script to execute, negating most XSS protection. Next.js 14 supports nonce-based CSP via next.config.ts + middleware. Replacing 'unsafe-inline' with a per-request nonce (or using 'strict-dynamic') would significantly harden both applications. The current production CSP is approximately as restrictive as no CSP for stored-XSS scenarios.

LOW
formatCents in tenant.ts: negative cents produces incorrect output
apps/product/src/lib/tenant.ts · lines 105–108

formatCents(-150) returns $-1.50 (dollars = -1, centsRemainder = -50 → %-50 with padStart). Negative cents should not appear in estimates (all amounts are >= 0), but the function is a shared utility that may be called with line adjustments or refund amounts in the future. Add a guard or sign handling. Also: the remainder cents % 100 is always 0..99 for positive inputs, but Math.trunc is not used for the dollars — for cents = 199, Math.trunc(199/100) = 1, remainder = 99. Correct for positive. Unclear for negative without Math.trunc.

LOW
TOTP window parameter is passed as epoch tolerance, not window count
apps/product/src/lib/mfa.ts · line 35

verifySync({ token, secret, epochTolerance: TOTP_WINDOW * 30 }) passes 30 seconds as epochTolerance. otplib's epochTolerance is measured in seconds, so this allows a ±30-second window, which is exactly ±1 TOTP period. The comment says "Allow ±1 window (30s each side)" — correct. However the TOTP_WINDOW = 1 constant suggests it is a window count, not a seconds value. If anyone reads the constant as "number of windows" and changes it to 2, the tolerance becomes ±60 seconds (2 windows), which is more than the RFC recommended 1-window tolerance but still manageable. The naming should be TOTP_EPOCH_TOLERANCE_SECONDS = 30 or the code comment should explain the arithmetic explicitly to prevent a future bug.

LOW
Outbox dispatch ignores finishOutboxMessage failure silently on success path
apps/product/src/lib/outbox-dispatch.ts · lines 266–270

On successful delivery, the await finishOutboxMessage(..., true, null) call is wrapped in a try/catch that swallows all errors with the comment "Lease expiry will re-claim." This means the email was sent but the row stays as claimed. When the 5-minute lease expires, claim_ready_outbox_messages will re-claim and re-send the email. The comment is correct but this is a real double-delivery risk (not just theoretical) for any transient DB failure during the finish call. The finish call should be retried at least once before letting the lease handle it.

LOW
PLATFORM_HOSTS set does not include localhost — classifyHost returns 'unknown' in dev
apps/product/src/lib/host.ts · lines 15–20

In local development, the request host is localhost:3000. hostnameOf('localhost:3000') = 'localhost', which is not in PLATFORM_HOSTS and does not match .usejbox.com, so classifyHost returns 'unknown'. The proxy file (if/when it runs) would rewrite to /platform. But every route that calls withTenant() and checks classifyHost(host) !== 'tenant' will throw TenantResolutionError('platform-host') (actually 'no-host' since the code maps anything non-'platform' to 'no-host'). Developers must set an explicit *.usejbox.com local domain or use DEVELOPMENT_FIELD_ORGANIZATION_ID. The README does not document this. Add localhost to PLATFORM_HOSTS, or document the required dev setup.

ℹ️ Info / Suggestions

INFO
packages/domain: ModuleKey type is disconnected from capability enforcement
packages/domain/src/index.ts

The four-gate entitlement model (subscription, feature purchase, owner activation, role capability) is clearly documented in the comment on ModuleKey. However, there is no runtime enforcement of gates 1–3 anywhere in the codebase — only gate 4 (role capability) is checked. The module entitlement system (resolveModulePrerequisites, unsatisfiedPrerequisites) has no call sites in the product app. Before inventory or scheduling are surfaced in the UI, the entitlement check path needs to exist.

INFO
No CORS headers on any API route
apps/product/src/lib/http.ts · apps/product/next.config.ts

The Field API and customer-facing estimate routes carry Cache-Control: private, no-store via privateJson() but no CORS headers. If a future mobile app or external client needs to call these APIs, every route will need CORS added. The global headers() in next.config.ts could add Access-Control-Allow-Origin: none as an explicit lock-down, making the intent clear and preventing accidental cross-origin access before CORS is intentionally opened.

INFO
Migration checksum uses entire file; comment edits will invalidate applied migrations
packages/database/src/migration-plan.mjs · checksumFor()

The SHA-256 checksum covers the full file source, including comments. Adding a clarifying comment to an already-applied migration will cause migrate.mjs to throw "changed after it was applied." This is stricter than necessary and will frustrate teams that annotate migrations post-hoc. A common alternative is to strip comments before hashing, or hash only the normalized SQL statements. The current design is documented nowhere as a gotcha for contributors.

INFO
No structured logging — console.error on every 503 path loses request context
apps/product/src/app/api/field/estimates/route.ts · lines 77, 169

Error paths use console.error('Estimate list failed.', error) with no request ID, tenant ID, or actor ID. The requestId is already available in the organization context store. Without structured logging, correlating a user-reported "estimates unavailable" with a log line in Fly/Vercel requires guessing time windows. At minimum, log the request ID and organization ID alongside every error before production launch.

INFO
control-plane: getOrganizationReadiness mixes control_app reads with contractor_app reads in one transaction — possible SET LOCAL ROLE ordering issue
apps/control/src/lib/control-plane.ts · getOrganizationReadiness · lines 213–253

The function calls provision([...statements]) which executes in a single transaction, switching roles via SET LOCAL ROLE. Statement order is: (1) control_app org query, (2) control_app set_application_context, (3) contractor_app config query, (4) contractor_app price book query. Step 2 switches to control_app and calls set_application_context but the role at that point is control_app not the login role — set_application_context is granted to PUBLIC so this executes. However, the organization context is set while still as control_app, and then used while as contractor_app. This works because set_config is session/transaction scoped, not role-scoped. It is correct but fragile — a reader must know set_config transcends roles. This should be documented in a comment.

INFO
AI prompt uses `user` role only — no system message for instruction following
packages/ai/src/index.ts · lines 195–196

buildPrompt() returns the entire prompt as a single user message. Best practice for instruction-following models (including Llama 3.1 405B on NVIDIA) is to put the persona/task in a system message and the dynamic inputs in the user message. The current single-user-message approach works but is more susceptible to prompt injection via input.notes (a free-text field). Splitting into system + user and escaping the notes field (at minimum, stripping known jailbreak prefixes) would reduce prompt injection risk.

✅ Notable Strengths

These are areas the codebase handles well and should be preserved as-is:

  • RLS isolation model — ENABLE + FORCE together on every tenant table, SECURITY DEFINER windows narrowly scoped, no BYPASSRLS anywhere. This is production-grade.
  • Integer-cents money arithmetic — BigInt for all intermediate products, divRoundHalfUp for all divisions, millipercent for all rates. No floats in the pricing path. Excellent.
  • Immutable estimate state machine — database-level triggers enforcing terminal-state lock plus the application-layer canTransition() guard is belt-and-suspenders done right.
  • Transactional DDL migrations — each migration and its ledger entry in one transaction. Checksum guards prevent silent schema drift.
  • JWT session revocation — per-jti field_sessions row; re-reads live membership on every request. Role changes propagate on the next request without waiting for token expiry.
  • Configration versioning and approval gate — immutable config documents, assertApprovalReady() as a separate check from structural validation, AI copy isolated from branding/tax/pricing.
  • Timing-safe comparisons — timingSafeEqual in cron-auth, customer-access-grants verification, and password verification. No timing oracle anywhere.
  • AsyncLocalStorage for tenant context — avoids global mutable state, making concurrent request safety structural rather than a comment.
